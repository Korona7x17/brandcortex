# Migrations

BrandCortex's own database only. The brand DB is out of scope here — we hold a read-only seam into it,
and changes there (like adding the `content_items` handoff table) belong to the brand's own migrations.

```bash
uv run alembic revision --autogenerate -m "add posts"
uv run alembic upgrade head
uv run alembic downgrade -1
```

Rules: every schema change ships with its migration in the same change; never edit a migration that has
been applied anywhere; always write a real `downgrade`.

## No baseline yet

`versions/` is empty — no migration has ever been generated, so there is nothing to migrate *from*. All
model changes to date (including `posts.asset_storage_key` and the `playbook` verification/prediction
columns) will land in the first autogenerated revision:

```bash
uv sync && uv run alembic revision --autogenerate -m "initial schema"
```

Hand-writing that baseline was deliberately skipped: a migration transcribed by eye has to match
SQLAlchemy's own DDL exactly across eight tables, and where it doesn't, the drift is silent until
production. Autogenerate against a live Postgres is one command and is correct by construction. Once
that first revision exists, the "migration in the same change" rule applies normally.
